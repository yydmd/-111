## 2026-09-03 定版前收尾：校准回落 + 独立复审修复 5 项（含 1 高 2 中）

- **背景**：用户要求定版前"补校准回落小修复 + 验证无其他 bug"。回落修复后，派独立审查代理对三轮竞速改动（2032232 → 工作区）做全新视角复审，确认 6 项不变量中 5 项成立、并发现 3 个真实缺陷 + 2 个低危，全部修复。

### 修复清单

1. **校准双向回落（本轮目标）**：`_record_accept_offset` 区间从 (0,10] 改为 [-5,10]——平台即时受理（偏移 ≤ 0）会把 EMA 拉回 0，陈旧偏移不再永久晚开火；0.2s 安全余量天然构成死区，小噪声不追。
2. **【高】父会枪异常路径缺 stop**：父枪抛非 ReservationError（如平台返回 JSON 数组导致 `.json()` 后 `.get` 抛 AttributeError）时，异常展开释放账号锁而 racer 仍被唤醒提交。修复：父枪块加 `except BaseException: stop.set(); raise`（stop 先于 opened）；同时客户端对非 dict 响应归类 SUBMIT_OUTCOME_UNKNOWN（已发出、格式异常、走核实）。
3. **【中】校准样本被串行阶段污染**：串行尝试在退避等待后发生，计入会形成"每轮比上轮晚"的正反馈自锁（慢性 303 账号可被顶到上限 5s）。修复：只取 volley 阶段信号（timing 含 page_ms 的父枪/racer 尝试）。
4. **【中】宽限期解析拖尾漏网**：racer 在解析阶段（尚未 POST、不在 submitting 集合）超过宽限时既不被 stop 也不被审计，函数返回后可与串行并发提交、产生无对账的第二笔预约。修复：宽限 join 后无条件 `stop.set()`；stuck 快照与审计追加移入同一 guard 块（消除快照/追加竞态的双矛盾记录）。
5. **【低】父枪确认占用后同座 racer 补枪**：新增 volley_dead 共享集合（guard 保护），racer 醒来后检查——"已占用绝不重试"在 volley 内同样严格成立。
6. **【低】解析层非 ReservationError 静默杀 racer**：race() 两处 `resolve_submission_page` 的 except 从 ReservationError 放宽为 Exception，意外崩溃落入下一级兜底而非让座位从审计消失。

### 验证

- pytest 96/96 连续两轮稳定（91 + 新增 5：父枪崩溃 stop、volley_dead 跳过补枪、宽限无条件 stop、racer 解析崩溃存活、非 dict 响应归类；校准端到端测试改为 volley 信号版）；upgrade_check 43/43；compileall 通过。
- 复审确认：测试改动无强断言降级；client.deadline 临时延长不可能给串行路径多余提交机会（延长仅发生在 stuck 分支，该分支在串行之前 return）。
- 六项不变量（303 不计预算 / 已占用绝不重试 / 未知结果绝不重提 / 首胜即停 / 校准异常零影响 / 打桩签名兼容）全部成立，各有测试钉住。

## 2026-09-03 速度升级：父会话参战 + 开火自动校准 + 自愈末轮完整链

- **背景**：run #235（竞速硬化版首战）遥测显示成功仍耗时 2.9 秒。三个数据结论：(1) 四场实战成功 100% 来自父会话完整解析链，racer 快捷路径 303 率 100%（token_age=0.0ms 排除 token 因素）；(2) 开抢后 ~1.5 秒内平台对一切请求回 303——开火时刻早于平台真实受理时刻，火力空打；(3) 串行兜底 0.3-0.6 秒间隔是恢复链路最慢一环。

### 修复（app/service.py）

1. **父会话参战**：poller 检测到窗口后，主线程直接用手头最新页面在开抢时刻提交（seats[0]，零额外取页，~1 个往返），**严格先于** racer（racer 延迟到父会枪出结果后才唤醒/出手）。父会话是唯一被实测验证能落地的通道，这把"已被验证的第一发"从排在最后提前到第一枪。结局汇入现有 outcomes 流程：303 不计预算、占用入 dead_seats、首胜即停、迟提交照常宽限+核实。
2. **开火时刻自动校准**：每次定时运行记录"首个真实受理"时刻（受理信号码：成功/座位占用/平台拒绝/限流/重定向），与开火时刻之差做 EMA（α=0.5，只记正偏移，截断 0-5 秒），持久化于 app_settings（key=`fire_accept_calibration`）。下次开火 = 配置时刻 + max(0, EMA − 0.2s 安全余量)。无样本时行为与旧版完全一致；运行消息注明"开火校准：按最近 N 次实测后移 X 秒"。校准异常绝不影响运行本身。
3. **自愈末轮走完整解析链**：racer 自愈的最后一轮（heals_left==0）先走 `resolve_submission_page` 完整链再回退快捷路径——对齐实战 4/4 成功路径，覆盖校准偏差的日子。
4. **串行兜底提速**：RETRY_WAIT_RANGE (0.3, 0.6) → (0.2, 0.45)，保留随机抖动。
5. **遥测补强**：每次尝试增加 `at`（提交起发的服务器纪元秒），父会枪记录 page_ms=0/token_age_ms（poller 页面年龄）。

### 零回归保障

- 四项历史不变量逐一核对未动（303 不计预算 / 已占用绝不重试 / 结果未知绝不重提 / 首胜即停）；父会枪完全走现有 `submit_once` 与 outcomes 流程。
- 校准读写全兜异常、无样本零行为变化；`_scheduled_fire_epoch(plan)` 签名兼容旧测试打桩。
- 验证：pytest 91/91 连续三轮稳定（87 旧 + 新增 4：父会枪即胜即停含 at 遥测、校准 EMA/拒绝异常偏移/无样本零偏移/有样本后移、自愈末轮确实调用完整链、定时运行端到端记入校准样本）；upgrade_check 43/43（volley 计数按父会枪语义更新为 12 发，heal 场景 098 改终局占用消除线程竞态）。

## 2026-09-03 竞速硬化：堵上两个实战暴露的薄弱点（racer 303 自愈 + 迟到提交审计）

- **背景**：run #230 实战复盘发现两个决定瞬间对决胜负的薄弱点：(1) 两次真实运行（#221、#230）的并行 volley 全部被 303 拒绝，胜利全靠数秒后的串行恢复——对面脚本只要瞬间落进一个干净请求就赢；(2) 客户端超时下限 1 秒使 POST 可合法跑到 deadline 之后，join 截止后迟到的成功不进审计、不触发核实（预约可能已生效但显示失败）。

### 修复（均在 app/service.py 开抢路径）

1. **racer 303 自愈**（`RACER_HEAL_ATTEMPTS=2`）：被 303 拒绝的 racer 立即在自己会话上重新取页并重提，恢复时间从秒级（退到串行）压到 ~1 个往返。只对 TOKEN_STALE 生效（平台明确"已拒绝、请刷新重提"，无重复提交风险）；SEAT_UNAVAILABLE/SUBMIT_OUTCOME_UNKNOWN 等行为不变；自愈前查 stop，首个成功即停的语义不变。
2. **错峰开火**（`RACER_STAGGER_SECONDS=0.05`）：racer 按优先级序位错峰（097 在 t0、每级 +50ms、总跨度 150ms），规避同账号毫秒级 N 连发的反爆发拒绝（两次实战的 3×303+1 占用模式）。优先级语义不变：越靠前越先发。
3. **迟到提交审计与核实**（`LATE_SUBMIT_GRACE_SECONDS=2.5`）：提交前登记座位、结局后移除（在途集合）；deadline 后有界宽限 join 让在途 POST 落地记审计；宽限后仍在途的座位 stop 阻新提交、补记 SUBMIT_OUTCOME_UNKNOWN——复用现有"未知结果→超星端核实"分支（found→SUCCESS / 无法核实→NEEDS_VERIFICATION），杜绝静默失败。核实时客户端临时续 8 秒 deadline（串行循环用本地 deadline 变量，不会多提交任何东西）。
4. **竞速遥测**：每次尝试记录 `page_ms`/`submit_ms`/`token_age_ms`/`heals`（attempt_details 的 timing 字段），volley 级窗口检测时刻与结果汇总写 service.log——用真实数据定位 303 根因、调优错峰参数（若实战仍整队 303，可增大 RACER_STAGGER_SECONDS 或减小 PARALLEL_SEAT_LIMIT 再观察）。

### 零回归保障（用户要求改动不引入新问题）

- 四项历史不变量逐一核对未动：TOKEN_STALE 不计入重试预算（自愈产生的 303 结果同样不计）、已确认占用座位绝不重试、SUBMIT_OUTCOME_UNKNOWN 绝不重提、首个成功即停。
- 串行路径、探测路径、Web 层零改动；宽限只在 deadline 已耗尽（串行本来无法运行）的场景介入，不延长账号锁占用。
- 验证：pytest 87/87（83 旧全量通过 + 新增 4：自愈原地成功含遥测断言、自愈有界、迟到提交审计+核实+客户端续命、错峰保序）；upgrade_check 43/43（38 旧 + 新增自愈恢复、迟到提核实场景；volley 303 场景计数按自愈语义更新为 11 发）。

## 2026-09-03 全面排查：17 项修复（含 01:29 定时计划未执行事故）

- **事故记录**：计划 6（房间 10713，座位 097→098→099→100，21:00-21:30）run_time 改为 01:29 并于 01:28:35 保存（目标日 2026-09-04，auto_context 已保存）。到点后**计划未执行**——无唤醒日志、无运行记录；界面仍显示"下次自动执行 2026-09-03 01:29"。
- **根本原因（scheduler.py:96-104，经日志 + app.db 实证）**：01:28:35 保存时新 run_time 的唤醒时刻（01:28:30）已过 5 秒，APScheduler 把 cron 排到明天；唯一兜底的"错过后补跑"被 `already_created` 去重查询静默吞掉——该查询只按 `(plan_id, target_date, trigger∈scheduled*)` 匹配，命中了当天 01:01 旧 run_time 产生的 FAILED 记录（run #221，同目标日 2026-09-04）。day_offset=1 使同日不同 run_time 的执行共享 target_date，去重键却不含运行日期与状态。
- **修复**：去重仅认可 **PENDING/RUNNING（在途）或 SUCCESS（已订上）** 的 run；FAILED 等失败终态意味着窗口已丢失，正是补跑要救的场景；真实重复预约仍由 SUCCESS 指纹查重 + 超星端核实两层安全网拦截。回归测试见 `test_catchup_after_failed_run_still_enqueues`。

### 本轮修复清单（三路代码审查 + 实证定位）

**P0（01:29 事故）**
1. `app/scheduler.py` 补跑去重加状态过滤（上述根因）。
2. `/api/plans` 新增后端 `next_run_at`（取自 APScheduler 任务的真实下次触发 + 30s 提前量），前端"下次自动执行"优先显示后端值，浏览器推算仅作后备——事故中正是纯前端推算掩盖了"已排到明天"的事实（smoke 实证：plan 6 现如实显示 2026-09-04 01:29）。

**P1（高危，直接影响抢座成功率）**
3. `app/service.py` 串行重试不再复用旧 `pre_resolved`：原 `pre_resolved = None` 只在成功路径执行，单座位 303 后的重试把被拒 token 原样再提交（上一事故根因"token 太旧"的单座位残留路径）。现改为提交前无条件消费。
4. 串行兜底轮换候选座位：整队 303 后刷新重试依次轮到 098/099，不再把预算全砸在 097（`round_tried` 轮换，dead_seats 绝不重试的不变量不变）。

8. 未识别的 30x 重定向从 `BLOCKED_BY_RISK`（终局风控、volley 直接 fatal、账号标记风控）降级为可重试 `HTTP_REDIRECT`。

### 已知未修问题（本轮记录在案，后续处理）

- deadline 临界 racer 迟到 ~1s 的 POST 落地后不在审计中、也不触发服务器核实（chaoxing_client 超时下限 1s 与 join 截止的缝隙）。
- `logged_in` 一次性闩锁：开抢途中 LOGIN_REQUIRED 无自动重登路径；克隆会话 cookie 是快照，可能与父会话分叉。

- 登录凭据走 URL 查询串（沿袭 upstream）；登录失败不区分验证码/锁定。
- `clock` 拒绝异常偏差后仍刷新 `_measured_at`（坏数据锁定 10 分钟）；`security.redact` 的裸 `enc` 子串会过度改写。
- 预算读活 plan 而非快照（30s 提前唤醒窗口内改计划会影响在跑任务）；racer 线程只捕获 ReservationError，其余异常静默无 outcome。
- 服务停机超过 90s 后恢复的当天计划静默丢失（补跑窗口外）；`shutdown(wait=False)` 可能让停机瞬间入队的 run 滞留 PENDING。
- `_solve_slider` 是死代码（UI 开关无效承诺）；legacy `utils/reserve.py` 请求无超时，接线前必须先补。
- 前端 planCache 仅在 load() 刷新，多标签页 last-write-wins；runs 轮询不刷新 plans 区。

## 2026-09-03 01:01 定时预约整队失败：TOKEN_STALE 耗尽重试预算（已修复）

- **事故记录**：测试1 / 缪迪 · 定时预约，目标日 2026-09-04，候选座位 097 → 098 → 099 → 100（默认 max_attempts=3）。
- **现象**：并行开抢 4 个座位全部失败——097/098/099 返回 `TOKEN_STALE`（平台 303："您在页面停留过久，本次操作安全验证已超时。请刷新后再提交预约"），100 返回 `SEAT_UNAVAILABLE`（该时间段已被占用）。运行记录终局显示"失败 / 座位不可预约"。

### 根本原因（三个叠加缺陷，均在 app/service.py）

1. **重试预算被 303 拒绝耗光（主因）**：并行 volley 的 4 次提交全部计入 `used_attempts`，而预算上限 `attempts = min(max(3, 4), 6) = 4`，串行兜底循环 `range(4, 4)` 为空——虽然 `TOKEN_STALE` 被归类为"可重试、需刷新页面"，但一次刷新重试都没有执行就终止了。
2. **token 取得太早**：预约窗口已开放的时段（如本次 01:01 测试），poller 首跳即判定"已开"并唤醒 racer，racer 在开抢时刻前约 2 秒取页面参数，再等到点提交——token 在线上老化，被平台按 303 拒绝。
3. **终局结论误导**：预算耗尽后取"最后一条结果"的错误码（座位 100 的 SEAT_UNAVAILABLE）作为整个运行的结论，掩盖了 3 个座位实际是可重试的 303 拒绝。

### 修复方案（app/service.py）

1. `used_attempts` 不再统计 `TOKEN_STALE` 拒绝：303 是平台明确的"已拒绝、请刷新后重提"，未预约成功任何东西，不应占用串行重试预算；整队 303 后串行刷新重试必定执行（已确认占用的座位仍绝不重试）。
2. racer 改为先 `_hold_until_fire` 对齐开抢时刻、再取页面参数，提交所用 token 尽可能新；真开抢竞速场景时序不变（窗口只在时刻点后打开，两种顺序等价）。
3. `_poll_until_open` 在窗口已可用且距开抢仍超过 0.3s 时，按松弛节奏（0.2s）持续刷新页面直到临近开抢，交给单座位路径 / racer 兜底的页面不再老化。
4. 若刷新重试后仍全部 303，终局如实报告 `TOKEN_STALE` 而非误报"座位不可预约"。
