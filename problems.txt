## 2026-09-11 实战失败复盘与运行分支切换：5 项缺陷修复

### 修复清单

1. **浏览器关闭被误报为页面不兼容**（`app/browser_reserve.py`）：Playwright 的 `TargetClosedError` 以及浏览器断连后连 `page.is_closed()` 都会抛错的情况，统一归类为 `BROWSER_WINDOW_CLOSED`。未提交时可进入既有的一次窗口恢复逻辑，不再落成 `BROWSER_PAGE_UNSUPPORTED`。
2. **无提交的中断被错误要求人工核实，并阻止安全补跑**（`app/service.py`）：恢复时按 `possibly_submitted` 分流；可能已提交仍为 `INTERRUPTED_NEEDS_VERIFICATION`，明确未提交改为 `FAILED / INTERRUPTED_SAFE_TO_RETRY`，允许调度器执行普通补跑。
3. **座位明确占用后的状态落库失败仍可能继续换座**（`app/browser_reserve.py`）：`SEAT_UNAVAILABLE` 分支现在检查 `checkpoint()` 返回值；账号或计划已停用、状态无法提交时立即设置取消信号，并保留未知提交保护。
4. **时钟校准失败后坏状态锁定 10 分钟**（`app/clock.py`）：成功测量仍缓存 10 分钟，失败或异常偏差改为 60 秒后重试，避免一次网络故障影响下一次开抢校准。
5. **独立升级检查误启真实浏览器并长期挂起**（`tests/upgrade_check.py`）：测试计划显式使用 `execution_mode="api"`；同时补齐成功去重夹具的请求指纹，使独立验收与生产语义一致。

### 验证与运行态

- `tests/upgrade_check.py`：43/43 通过（约 4 秒，不再挂起）。
- `tests/test_core.py` + `tests/test_browser.py`：209/209 通过；`compileall` 通过；`git diff --check` 无错误。
- 当前运行分支为 `codex/risk-control-compat`，健康检查显示数据库、调度器正常且无活动任务；原 `local-web-refactor` 工作区保留但没有运行进程。

## 2026-09-10 检测面修复（N1 第一步）：移除关键路径上的"非页面"列表请求

- **背景**：用户明确第二根轴是**防脚本检测**（不只是数据一致性）。复查发现程序周边只读请求不经过浏览器页面，头签名与页面 XHR 明显不同；且提交之前那一次列表核对发生在**关键路径**上。

### 实测证据（已固化为可复现脚本 `scripts/probe_request_headers.py`）

纯本地回环（不触官方站、不读库/资料、无窗口）对比：

| 请求头 | 页面内 XHR | `context.request`（`lookup()` 用的） |
|---|---|---|
| `Referer` | 有 | **无** |
| `Sec-Fetch-Dest / Mode / Site` | 有 | **无** |
| `sec-ch-ua / -mobile / -platform` | 有 | **无** |
| `accept-encoding` | `gzip, deflate, br, zstd` | `gzip,deflate,br` |

另：`app/clock.py:74` 的时钟探测用 Python `requests`，UA 写死裸 `Mozilla/5.0`（典型脚本签名），目标是官方站（`clock.py:28-29`）。

### 关键事实（决定改法）

核对官方选座页脚本留存（生产工作区 `data/browser-inspection/select.js`，81KB）：它**只调用** `data/apps/seat/getdrawseat` 与 `data/apps/seat/seatgrid/roomid`，**从不调用** `/data/apps/seat/index`，全文无 `curReserves`。
→ 所以"提交前核对"所用的列表接口，**官方页面自己根本不发**。原计划的"复用页面已有数据（零请求）"不可行；该请求即使补上浏览器头，仍是页面流程外的动作。

### 改动（`app/browser_reserve.py`）

**移除开火之后的那次核对**（原 `tick("RUNNING","提交前核对已有预约")` + `lookup()` + 两个早退分支），保留**开火之前**的那次。理由与收益：

1. 它要查的是"**本账号**是否已有该时段预约"，而开抢瞬间本账号列表必然为空 —— 有价值的是开火前那次，不是开火后那次；
2. 它位于关键路径：每次候选在"平台开抢时刻"与"点击提交"之间多出一次往返；
3. 每个候选少一次"页面不会发的请求"（每候选 2 次 → 1 次，6 候选即 12 次 → 6 次）；
4. `submission_baseline` 自动改由开火前那次结果提供（语义上更正确：真正的"提交前基线"）。

**能力保留**：开火前核对仍在；结果不明时的对账（`reconcile` 内的 `lookup`）仍在；本地去重与 `possibly_submitted` 阻断仍在；页面禁用态判断（`prepare()` 已在用 `cls==='noSelect'`）仍在。
**已知代价**：开火瞬间到点击之间不再二次核对，理论上存在"本账号在同一瞬间被别的设备约到"的极小窗口；由平台自身拒绝（座位已被预约 → 换座）与提交后对账兜底。

### 验证

- `tests/test_browser.py` 106/106 通过（新增断言：`success` 场景下**提交前的列表读取恰好 1 次**，锁死"开火后不再有列表请求"）；`tests/test_core.py` 99/99 通过。
- 全链路 29 个模拟场景（含 merged / adjacent_merge / existing_disabled / seat_fallback / list_delay / stale_* / rate_* / risk）全部通过，说明相邻合并、冲突、既有预约跳过等语义未受影响。

### 涉及文件

- `app/browser_reserve.py`、`tests/test_browser.py`、`scripts/probe_request_headers.py`（新增）、`data/qa/upgrade-plan.md`

## 2026-09-10 升级执行 P0 + P2-1：现役链路补 303「刷新后重提」通道

- **背景**：`data/qa/speed-safety-assessment.md` 把"现役浏览器链路对平台 303『页面停留过久，请刷新后再提交』的处理"列为最高优先待确认项。本轮先做纯离线判定（不触网、不跑真实预约），确认缺口成立并修复。方案见 `data/qa/upgrade-plan.md`。

### P0 判定（离线夹具，三种形态）

1. `stale_plain`（不含"安全验证"的刷新文案）修复前：无任何分支匹配 → `pending` 保持 True → 20s 只读对账 → `SUBMIT_OUTCOME_UNKNOWN`，**完全不重提**。
2. `stale_security`（平台真实文案，同时含"安全验证"与"页面停留过久"）修复前：被**误判为人工挑战** → 开一次同座位续提但要求人工在原窗口动作，人不动作则一直等到任务截止。
3. `stale_redirect`（原始 303 + Location、无可解析正文）修复前：结果未知。

结论：**"官方页面 JS 会替程序兜住 303"的假设不成立**——闸门会 abort 任何同座位的二次提交（`app/browser_reserve.py:449-452`），而唯一解锁通道原本只在验证码分支开启（`:550-558`）。同一条平台文案，API 链路按 `TOKEN_STALE` 自动刷新重提（法理见 `app/service.py:39-42`），浏览器链路却退化为"等人工 / 结果未知"。

### 修复（P2-1）

- 闸门新增 `REFRESH_REJECTION_WORDS` 与 `refresh_pending` / `refresh_serial`，分类**排在人工挑战分支之前**（因真实文案同时含"安全验证"）。
- 复用既有"显式解锁"语义：`continuation = challenge_pending or refresh_pending`，解锁在放行时**被消费**；**`attempted` 未做任何放宽**，同座位第三枪仍被拒。
- 座位循环由 `for` 改为有界 `deque`：收到刷新拒绝时把**同一座位** `appendleft` 重新入队、立即重走完整每座位流程（重新加载页面取得新 token + 提交前重复核对 + 再点击），上限 `REFRESH_RETRY_LIMIT = 1` 次/座位；超限如实报 `TOKEN_STALE`，不再误报"座位不可预约"或"结果未知"。

### 验证

- `tests/test_browser.py` 106/106 通过（新增 3 个 `stale_*` 场景 + 闸门级不变量单测 `test_refresh_rejection_arms_one_same_seat_retry_without_loosening_attempted`）；`tests/test_core.py` 99/99 通过。
- 为规避受限环境下的 Chromium 驱动抖动，浏览器用例分块运行（36+35+18+17）后逐块全绿。

### 遗留

- **P2-1b**：原始 `303 + Location`（无可解析正文）仍无法分类。需先采集一次真实 303 的响应形态（状态码 / 正文 / 重定向目标），避免把"会话失效需重登"误判成"可重提"。
- P1（速度度量）、P2-2/P2-3（开火补偿、jitter）、P2-4/P2-5、P3（凭据卫生、死代码、文档计数）均未开始。

## 2026-09-10 复审 216a665「优化浏览器风控兼容与请求闸门」：6 项缺陷核实并修复（1 高 + 2 中）

1. **【高】限流被判成风控终局，同一错误码两条链路两种语义**（`app/browser_reserve.py`）：收到“操作频繁/过于频繁/请勿频繁/请求频繁/稍后再试”时原以 `BLOCKED_BY_RISK` + `terminal_code=RATE_LIMITED` 停手整轮，与 `service.py:_RETRYABLE_CODES`、`chaoxing_client.py` 的“限流不是风控判决”口径及前端 `RATE_LIMITED` 文案相反。改为 `checkpoint("RUNNING", "官方提示操作频繁；已退避并继续检查下一候选", False, seat, "RATE_LIMITED")`，置 `rejected` 并记录 `rejection_code/rejection_message`，退避 `RATE_LIMIT_BACKOFF_MS=500` 后继续下一候选；只有“非法操作/异常操作/风险控制/风控拦截/访问被拒绝”仍是终局。运行状态回落为 `FAILED`，界面不再同时出现“风控拦截 + 自动退避重试”。

## 2026-09-03 定版前收尾：校准回落 + 独立复审修复 5 项（含 1 高 2 中）

- **背景**：用户要求定版前"补校准回落小修复 + 验证无其他 bug"。回落修复后，派独立审查代理对三轮竞速改动（2032232 → 工作区）做全新视角复审，确认 6 项不变量中 5 项成立、并发现 3 个真实缺陷 + 2 个低危，全部修复。

### 修复清单

1. **校准双向回落（本轮目标）**：`_record_accept_offset` 区间从 (0,10] 改为 [-5,10]——平台即时受理（偏移 ≤ 0）会把 EMA 拉回 0，陈旧偏移不再永久晚开火；0.2s 安全余量天然构成死区，小噪声不追。
2. **【高】父会枪异常路径缺 stop**：父枪抛非 ReservationError（如平台返回 JSON 数组导致 `.json()` 后 `.get` 抛 AttributeError）时，异常展开释放账号锁而 racer 仍被唤醒提交。修复：父枪块加 `except BaseException: stop.set(); raise`（stop 先于 opened）；同时客户端对非 dict 响应归类 SUBMIT_OUTCOME_UNKNOWN（已发出、格式异常、走核实）。
3. **【中】校准样本被串行阶段污染**：串行尝试在退避等待后发生，计入会形成"每轮比上轮晚"的正反馈自锁（慢性 303 账号可被顶到上限 5s）。修复：只取 volley 阶段信号（timing 含 page_ms 的父枪/racer 尝试）。
4. **【中】宽限期解析拖尾漏网**：racer 在解析阶段（尚未 POST、不在 submitting 集合）超过宽限时既不被 stop 也不被审计，函数返回后可与串行并发提交、产生无对账的第二笔预约。修复：宽限 join 后无条件 `stop.set()`；stuck 快照与审计追加移入同一 guard 块（消除快照/追加竞态的双矛盾记录）。
5. **【低】父枪确认占用后同座 racer 补枪**：新增 volley_dead 共享集合（guard 保护），racer 醒来后检查——"已占用绝不重试"在 volley 内同样严格成立。
6. **【低】解析层非 ReservationError 静默杀 racer**：race() 两处 `resolve_submission_page` 的 except 从 ReservationError 放宽为 Exception，意外崩溃落入下一级兜底而非让座位从审计消失。

### 验证

- pytest 96/96 连续两轮稳定（91 + 新增 5：父枪崩溃 stop、volley_dead 跳过补枪、宽限无条件 stop、racer 解析崩溃存活、非 dict 响应归类；校准端到端测试改为 volley 信号版）；upgrade_check 43/43；compileall 通过。
- 复审确认：测试改动无强断言降级；client.deadline 临时延长不可能给串行路径多余提交机会（延长仅发生在 stuck 分支，该分支在串行之前 return）。
- 六项不变量（303 不计预算 / 已占用绝不重试 / 未知结果绝不重提 / 首胜即停 / 校准异常零影响 / 打桩签名兼容）全部成立，各有测试钉住。

## 2026-09-03 速度升级：父会话参战 + 开火自动校准 + 自愈末轮完整链

- **背景**：run #235（竞速硬化版首战）遥测显示成功仍耗时 2.9 秒。三个数据结论：(1) 四场实战成功 100% 来自父会话完整解析链，racer 快捷路径 303 率 100%（token_age=0.0ms 排除 token 因素）；(2) 开抢后 ~1.5 秒内平台对一切请求回 303——开火时刻早于平台真实受理时刻，火力空打；(3) 串行兜底 0.3-0.6 秒间隔是恢复链路最慢一环。

### 修复（app/service.py）

1. **父会话参战**：poller 检测到窗口后，主线程直接用手头最新页面在开抢时刻提交（seats[0]，零额外取页，~1 个往返），**严格先于** racer（racer 延迟到父会枪出结果后才唤醒/出手）。父会话是唯一被实测验证能落地的通道，这把"已被验证的第一发"从排在最后提前到第一枪。结局汇入现有 outcomes 流程：303 不计预算、占用入 dead_seats、首胜即停、迟提交照常宽限+核实。

## 2026-09-03 01:01 定时预约整队失败：TOKEN_STALE 耗尽重试预算（已修复）

- **事故记录**：测试1 / 缪迪 · 定时预约，目标日 2026-09-04，候选座位 097 → 098 → 099 → 100（默认 max_attempts=3）。
- **现象**：并行开抢 4 个座位全部失败——097/098/099 返回 `TOKEN_STALE`（平台 303："您在页面停留过久，本次操作安全验证已超时。请刷新后再提交预约"），100 返回 `SEAT_UNAVAILABLE`（该时间段已被占用）。运行记录终局显示"失败 / 座位不可预约"。

### 根本原因（三个叠加缺陷，均在 app/service.py）

1. **重试预算被 303 拒绝耗光（主因）**：并行 volley 的 4 次提交全部计入 `used_attempts`，而预算上限 `attempts = min(max(3, 4), 6) = 4`，串行兜底循环 `range(4, 4)` 为空——虽然 `TOKEN_STALE` 被归类为"可重试、需刷新页面"，但一次刷新重试都没有执行就终止了。
2. **token 取得太早**：预约窗口已开放的时段（如本次 01:01 测试），poller 首跳即判定"已开"并唤醒 racer，racer 在开抢时刻前约 2 秒取页面参数，再等到点提交——token 在线上老化，被平台按 303 拒绝。
3. **终局结论误导**：预算耗尽后取"最后一条结果"的错误码（座位 100 的 SEAT_UNAVAILABLE）作为整个运行的结论，掩盖了 3 个座位实际是可重试的 303 拒绝。

### 修复方案（app/service.py）

1. `used_attempts` 不再统计 `TOKEN_STALE` 拒绝：303 是平台明确的"已拒绝、请刷新后重提"，未预约成功任何东西，不应占用串行重试预算；整队 303 后串行刷新重试必定执行（已确认占用的座位仍绝不重试）。
2. racer 改为先 `_hold_until_fire` 对齐开抢时刻、再取页面参数，提交所用 token 尽可能新；真开抢竞速场景时序不变（窗口只在时刻点后打开，两种顺序等价）。
3. `_poll_until_open` 在窗口已可用且距开抢仍超过 0.3s 时，按松弛节奏（0.2s）持续刷新页面直到临近开抢，交给单座位路径 / racer 兜底的页面不再老化。
4. 若刷新重试后仍全部 303，终局如实报告 `TOKEN_STALE` 而非误报"座位不可预约"。
