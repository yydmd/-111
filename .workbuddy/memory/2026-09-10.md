# 2026-09-10 结论留存：迄今改动的"速度净效果"（用户会反复问，直接引用）

**结论：没有变慢；但也没有实质变快。真正的提速项还没做。**

- **路由收窄（216a665）**：离线基准实测 进入 Python 回调的请求数 150 → 50（−67%），但网络请求数不变（150/150）；三个毫秒指标（click_to_request / gate_handler / request_to_response）的差值在 **+8.5ms ~ −2.0ms 之间摆动、方向不稳定**，落在重复运行的抖动带内（`data/qa/anti-detection-benchmark.json`）。
  - 机制解释：提交路径本身的回调次数与每次工作量都没变；`context.on("response", ...)` 仍对**全部**响应回调，这部分开销一点没减。所以"收窄路由"不可能让"点击→请求"变快；唯一可能的间接收益是减少工作线程（sync Playwright 的回调跑在该线程）在开火时刻的争用——**未测量，仅机制推断**。
  - 注意基准夹具每轮只发 3 个请求，真实页面静态资源更多 → 真实世界的回调减少量比 150→50 更大，但同理会减少的是**非提交路径**的开销。
- **限流改可重试（第一轮 bug#1）**：净变快（修前第一枪被限流即整轮放弃 = 0 机会；修后 +500ms 退避继续换座），代价是每次限流让出 0.5s。
- **303 刷新重提（P2-1）**：净大幅变快（修前：等人工 / 20s 对账后"结果未知"；修后：一次页面重载即重提），代价是重提那一轮多一次页面加载。
- **快乐路径（没被限流、没 303）完全没变**；计时埋点、闸门正则、守卫比较的开销可忽略（单元闸门 P95 0.027ms）。
- **还无法用数据回答"开抢那一刻快了多少"**：`fire_epoch` 与受理时刻都没落库——这正是轮次 A 要解决的。
- 真正的提速杠杆仍未动：开火补偿 EMA、jitter、dense 时钟、开火后固定开销（只读核对 + 二次 prepare ≈ +1×RTT）、限流后同座位重试。

# 2026-09-10 目标轴修正 + 路线复核（用户明确第二根轴是"防脚本检测"）

用户明确：目标是 **速度 × 防脚本检测**，此前我按"安全=数据一致性"评估是偏的。数据一致性仍是底线，但"是否兼得"此后按 **"平台看到的请求是否像正常用户流量"** 判。复核写入 `data/qa/upgrade-plan.md` §9（文首加了目标轴修正说明）。

## 本轮实测（关键证据，已固化为可复现脚本）
新增 **`scripts/probe_request_headers.py`**（纯本地回环 127.0.0.1，不触官方站、不读库/资料、无窗口）。实测：

| 头 | 页面内 XHR | `context.request`（`lookup()` 用的） |
|---|---|---|
| Referer | 有 | **无** |
| Sec-Fetch-Dest/Mode/Site | 有 | **无** |
| sec-ch-ua / -mobile / -platform | 有 | **无** |
| accept-encoding | `gzip, deflate, br, zstd` | `gzip,deflate,br` |
| User-Agent | 浏览器 UA | 本次一致 |

→ `lookup()`（`browser_reserve.py:803-823`）发出的请求**不可能来自页面**，且调用点就在每次提交之前（`:1004` 与 `:1019`，每候选 2 次，最多 12 次）。另外 `clock.py:74` 的时钟探测用 Python `requests` + 字面量 `Mozilla/5.0`（典型脚本签名），目标是官方站（`clock.py:28-29`）。
**这是当前路线上最真实的检测暴露面**，而修复方向能让两根轴同时受益（改从页面内发起，请求数不增）。

## 复核结论：大方向对，4 处要纠正
- **R1 目标没度量**：没有任何检测面指标（每轮请求数、提交前请求密度、限流/风控/303 命中率）。
- **R2 实现与策略不一致**：提交是页面发出的（头正常），周边只读请求不是 → 上面实测。
- **R3 部分提速候选反向**：并发/错峰提交、"限流后同座位重试"会增加异常请求特征（项目自己记录过：1ms 内相同突发被整批拒绝 `service.py:76-79`；高频请求触发账号风控警告 GitHub #89 `service.py:29-33`）。
- **R4 没有准入检查**：提速项缺"必须先过检测面检查"的约束。
- 双赢项（同时利好两根轴）：**303 自动重提已做**（替代了原本 20s 密集只读对账 ≈10 次 GET）；jitter；压缩开火前核对次数。

## 新增 N 系列计划（优先级高于原 P2-4/P2-5）
- N1 把 `lookup()` 改为页面内发起（优先复用官方页面已有的列表调用/页面状态，其次页面内 same-origin fetch）——检测面↑↑、请求数不增。
- N2 时钟探测去脚本签名（页面内同源读 `Date`），并把 dense 探测移出开火前关键窗。
- N3 检测面度量（并入轮次 A，否则无法回答"是否兼得"）。
- N4 "限流后同座位重试"（原 P2-5）**降级为默认不做**。
- 原轮次 A 扩展为 A+N3；轮次 B 先做 N2 再做 dense；原 P2-4 改为优先做 N1，"并发核对"方向放弃。

## 待用户拍板的边界问题
从页面内发起 `fetch` 属于"注入脚本到官方页面"。项目既有立场是"只点官方按钮、不设 Vue 状态、不调用其 submit/captcha 方法"——fetch 读列表**不违反**该约束，但比"纯点击"更主动。更严格的替代方案是**只读页面已有的预约列表状态**（不自己发请求）。已在 §9.6 列为决策项。

# 2026-09-10 续：N1 第一步已落地（改产品代码）——移除关键路径上的"非页面"列表请求

## 决定与理由
那次"提交前核对"查的是"**本账号**是否已有该时段预约"，而**开抢瞬间本账号列表必然为空** → 真正有价值的是**开火前**那次。开火后那次同时踩三个坑：① 在关键路径上（让开枪慢约一个往返）② 是页面不会发的请求（已查明官方页面不调该端点）③ 查的是几乎必然为空的列表。

## 改动（`app/browser_reserve.py`）
删除"开火后核对"（原 `tick("RUNNING","提交前核对已有预约")` + `lookup()` + 两个早退分支），保留开火前那次；`submission_baseline` 自动改由开火前结果提供（语义更正确）。
- 每候选列表请求 **2 → 1 次**（6 候选：12 → 6）
- 关键路径（开火→点击）内请求 **1 → 0 次**；剩下的只有纯 DOM 的第二次 `prepare()`
- 代码内写了注释说明理由，防止后人当缺陷"修回去"
- 保留：开火前核对、`reconcile` 里的对账、本地去重、`possibly_submitted` 阻断、页面禁用态判断（`prepare()` 的 `cls==='noSelect'`）

- **顺带达成**：原 P2-4 的"去掉一次往返"目标已由本改动完成；P2-4 剩下的"并发核对"方向放弃
